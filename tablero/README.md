# Consola de Soporte CMQ — Base de Conocimiento

Aplicación web (un solo archivo HTML) para el soporte de la mesa de ayuda de Jira,
con conexión en vivo a los proyectos **Quilmes (SG)** y **Cervepar (CERVEPAR)**.
Reúne el historial de tickets, una matriz de respuestas para Nivel 1, análisis de
tiempos y métricas, todo separado por cliente.

---

## Archivos del proyecto

| Archivo | Qué es |
|---|---|
| `Consola_Soporte_CMQ.html` | La app. Se abre en el navegador (doble clic). No necesita instalación. |
| `run_local.py` | Servidor local (Flask) que corre el conector de Jira en tu PC y le da datos a la app, con CORS. También guarda tus ajustes. |
| `main.py` | Tu conector de Jira. Desde v10 es una reescritura (`jira_connector_sla.py` renombrado a `main.py`) enfocada en SLA real + Request Type real — ver Registro de cambios v10. |
| `kb_state.json` | Ya no se usa para guardar (desde v30 eso va a Firebase, ver Registro de cambios). Puede seguir existiendo como resabio de versiones previas. |
| `README.md` | Este documento. |

> Nota: el token de Jira vive **solo** dentro de `run_local.py`, en tu PC. No subas ese archivo a GitHub ni lo compartas.
>
> Desde v30, los datos cargados (fichas, clientes, tickets de Telemática) se guardan en **Firebase (Firestore)**, no en `kb_state.json` — así la app funciona igual esté hosteada en la web o corriendo local. El token de Jira no tiene nada que ver con esto y sigue siendo 100% local.

## Cómo correrlo (local, en VS Code)

1. Instalar Python (marcando "Add Python to PATH") y la extensión **Python** de VS Code.
2. En una carpeta, poné juntos: `main.py` (tu conector), `run_local.py` y `Consola_Soporte_CMQ.html`.
3. Instalar Flask una sola vez, en la terminal:
   ```
   pip install flask
   ```
4. Abrir `run_local.py` y pegar tu **API token de Jira** en `CONFIG` (usar un token vigente; si compartiste alguno, revocalo y generá otro en `id.atlassian.com` → Security → API tokens).
5. Correr el servidor:
   ```
   python run_local.py
   ```
   Tiene que decir `Escuchando en http://localhost:8787`. Dejá esa terminal abierta.
6. Probar en el navegador: `http://localhost:8787/?query=todos&proyecto=CMQ` → devuelve JSON con `registros`.
7. Abrir `Consola_Soporte_CMQ.html` (doble clic, como archivo local) → pestaña **Cargar Jira → Conexión API** → pegar `http://localhost:8787` → **Traer datos**.

> Importante: abrir la Consola como **archivo local** (no desde una web https), porque el navegador bloquea llamadas a `localhost` desde https (contenido mixto).

## Conexión por API

La consola consume el servidor local (o una función en la nube) con `?query=...&proyecto=...`.

- **Consultas** (`query`): `todos`, `abiertos`, `en_progreso`, `resueltos_hoy` / `_semana` / `_mes`, `creados_hoy` / `_semana`, `sin_asignar`, `alta_prioridad`.
  ⚠️ `vencidos_sla` y `comparativa` están en el selector de la Consola pero el conector actual (`main.py` desde v10) no las tiene mapeadas — caen al JQL genérico (todo el proyecto) en vez de filtrar. Pendiente: o se sacan del selector, o se agregan a `jql_for()` en `main.py`.
- **Proyecto** (`proyecto`): vacío = ambos, `CMQ` (clave real `SG`) o `CERVEPAR`.
- **max_results**: opcional, tope de tickets a traer. Sin especificar = sin límite (trae todos los que matchean el JQL, paginando).
- **debug=fields**: `?debug=fields` devuelve qué campo de Jira se usó para Request Type y cuáles para SLA, sin traer tickets — útil para diagnosticar si el conector no encuentra un campo en otra instancia de Jira.
- **Modo reemplazo**: cada consulta **reemplaza** la base para que los números coincidan exacto con Jira (no se acumula). Botón **Vaciar base** para empezar de cero.

## Sincronización de ajustes (kb_state.json)

Tus ediciones se guardan en tu PC a través del servidor local, de forma automática:

- Al **abrir** la Consola, carga tus ajustes desde `/kb/state`.
- Al **reasignar un ticket** o **guardar clientes**, los manda a `/kb/save` (se escribe `kb_state.json`).
- Si el servidor no está corriendo, la Consola igual guarda en el navegador como respaldo.
- Para compartir con el equipo: pasarles el `kb_state.json`.

Guarda **solo ajustes** (reasignaciones + configuración de clientes). Los tickets siempre vienen de Jira.

## Cómo está organizada la información

**Clientes por prefijo del ticket.** El cliente se detecta por el código:
`SG-` → **Quilmes**, `CERVEPAR-` → **Cervepar**. Se configura en la pestaña **Clientes**
(nombre, prefijo, color, y palabras clave de respaldo). Se puede reasignar un ticket a mano.

**Interno vs. cliente** (para métricas de respuesta):
- Equipo interno (soporte): Diego Ferreira, Lucas Di Luca, Melisa Aranda, Agustina Vallejos, Marcos Marin, Julian Toros, Oscar Fuentealba, Soporte Técnico.
- Contactos de cliente (no cuentan como soporte): paula cerrudo, Nahir Duarte, Gustavo Vergara, y el resto de remitentes externos.

**Secciones:**
- **Panel**: KPIs + todos los gráficos + tiempos. Reacciona a los filtros.
- **Matriz N1**: por tipo de desagío — síntoma, datos a pedir, pasos, plantilla de respuesta (copiable), a quién escalar y tickets de referencia.
- **Tickets**: historial con filtros multi-selección (tipo, estado, responsable) y contadores dinámicos; búsqueda; reasignación de cliente.
- **Clientes**: configuración de clientes y detección.
- **Ejecutivos**: ficha por cliente (estado Demo/Cliente fijo, logística, referentes, medio de gestión, notas) y cartera agrupada por referente comercial CSTT. Ver v12 en el registro de cambios.
- **Cargar Jira**: conexión API + carga de archivos (export `.doc/.html` o respaldo `.json`) + exportar `.json` / `.csv`.

**Filtros interactivos**: multi-selección en tipo, estado y responsable; actualizan KPIs y gráficos del Panel; los contadores de cada filtro se ajustan según lo ya filtrado (facetas). El selector de cliente (arriba) acota todo por proyecto.

**Tiempos** (con las fechas reales de Jira vía API): 1ª respuesta interna, 1ª respuesta del cliente, y resolución total (creación → resolución). Se cuentan **solo en horario hábil: lunes a viernes de 8:00 a 17:00** — sábado, domingo y las horas fuera de ese rango no suman. Se muestran en horas si son menos de un día hábil (9h), o en días hábiles si son más. Hay un desglose de 1ª respuesta interna por tipo para ver dónde mejorar.

### Coordinación entre sesiones

Mientras se trabajaba esto, había otra sesión de Claude Desktop editando el mismo `Consola_Soporte_CMQ.html` (y después también `main.py`) en simultáneo (mismo usuario, dos IAs). Guardar el mismo archivo desde dos lados sin coordinación pisó cambios de ambas partes varias veces (horario hábil, tarjeta de comparación por cliente, contador de incumplidos, y una vez `main.py` completo volvió a la versión sin corregir). Regla de trabajo desde acá:
- **Antes de tocar un archivo compartido, releerlo entero** (no asumir que sigue como en el último mensaje) — así se detectan reversiones o cambios de la otra sesión antes de pisarlos.
- **Todo cambio se documenta acá**, en el momento en que se hace, no al final de la sesión.
- El **contrato de datos** que arma `main.py` (qué claves trae `sla`, `registro`, etc.) queda documentado en el docstring de `main.py` — si una sesión lo cambia, hay que actualizar `ticketTimes()` en el HTML en el mismo momento, o los tiempos vuelven a mostrar "—".
- Antes de que cualquiera de las dos sesiones guarde una edición grande, conviene avisar en el chat y esperar confirmación de que la otra está en pausa.

### v29 (2026-07-30) — Corregido el cálculo de "tiempo estimado" en Telemática (antes ignoraba la hora cargada)

- **Bug real encontrado y corregido**: el campo que ahora se llama "Tiempo estimado" (antes "Tiempo", en la tarjeta de cada ticket, en los gráficos "por tipo"/"por cliente" y en la tabla de Panel) se calculaba comparando solo las **fechas** de inicio y fin a medianoche, **ignorando por completo la hora cargada** (`hora_inicio`/`hora_resolucion`). Por eso un ticket resuelto el mismo día siempre daba "0h" sin importar cuántas horas reales había llevado, y en general el número no reflejaba las horas cargadas — es lo que viste como "1 hora" en vez de reflejar el trabajo real.
  - **Corrección**: nueva función `teleEstimadoMs(t)` que arma la fecha+hora completa de inicio y de fin (cuando la hora está cargada; si no, cae a medianoche como antes para no romper tickets viejos) y calcula el tiempo **hábil** (lunes a viernes, 8 a 17h) entre esos dos instantes exactos — la misma lógica de horario hábil que ya se usa para los tickets de Jira, pero ahora aplicada con precisión de horas y no solo de fechas.
  - **Aclaración importante sobre los dos números**: "Tiempo asignado" (reloj real, sin filtrar) y "Tiempo estimado" (solo horas hábiles dentro de ese rango) miden cosas distintas — el estimado va a ser **igual o menor** al asignado, nunca mayor, porque es un subconjunto de tiempo dentro del mismo rango (excluye noches, fines de semana y fuera de horario). Por ejemplo: un ticket de 09:00 a 18:00 el mismo día da *Tiempo asignado: 9h* y *Tiempo estimado: 8h* (se descuenta la hora entre las 17 y las 18, fuera de horario laboral). Un ticket de viernes 16:00 a lunes 10:00 da *Tiempo asignado: 2d 18h* (reloj real, incluye el fin de semana) y *Tiempo estimado: 3h* (1h del viernes + 2h del lunes, se salta el fin de semana entero).
  - Se actualizaron también los nombres y formatos para que ambos se vean con el mismo estilo "Xd Xh" (antes "Tiempo" usaba un formato en días decimales tipo "1.5d" que no podía mostrar algo como "1d 1h"; ahora usa el mismo formateador que "Tiempo asignado").

### v35 (2026-07-31) — Bug real: "Traer datos" fallaba en otras PC con "todos" (funcionaba en la mía) — el Worker ahora trae los tickets de a páginas cortas

El problema era el **tiempo**: "todos" para un solo proyecto hace ~34 llamadas seguidas a Jira (una por página de 100 tickets, tienen que ser en orden porque cada una necesita el token de paginación de la anterior) antes de devolver la respuesta completa. En vez de seguir insistiendo por CLI, se desplegó el código nuevo pegándolo directo en el editor online del dashboard de Cloudflare ("Edit code" → pegar → Deploy) — mismo resultado, sin depender de la sesión de la terminal.
